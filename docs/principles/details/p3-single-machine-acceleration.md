# Principle 3: Single-Machine Acceleration & Pluggable Sandboxing

## Detailed Specification & Rationale

* **Core Law**: The core runtime must achieve maximum throughput and minimal latency on a single machine, with optional, pluggable sandboxing for safe local execution.
* **Strict Rule**:
  - **Zero-Broker Default**: On the single-machine path, event dispatch between agents must not traverse an out-of-process message broker. Single-host execution runs directly in-memory (in-process async queue / zero-copy coroutine dispatch). External message brokers (Redis, RabbitMQ) are optional distributed extensions, never mandatory — they may be added for multi-host deployments, but their absence must never block or degrade single-machine operation.
  - **Selective Sandboxing**: Tool execution defaults to filesystem isolation (`isolation_level="workspace"`). Stronger isolation (`container`, `wasm`) is available by user configuration for untrusted workloads. Direct host execution (`none`) remains supported but is an **explicit opt-in** for trusted local work — it must never be reached by defaulting.
  - **A weaker level is never selected implicitly**: an artifact — a synthesized skill, a remote A2A task, an MCP tool — may *request* an isolation level, and the effective level is the **stronger of the request and the runtime's floor**. An artifact may ask for more isolation than the floor requires; it can never obtain less.
    > Stated as a comparison rather than as "clamping", because clamping has no fixed direction: the same operation reads as clamping *down* if you measure privilege and *up* if you measure isolation, and that ambiguity is how an escalation gets written by someone who read the sentence the other way.
  - **Isolation is not the credential boundary**: `workspace` bounds writes; it does not scrub the environment or restrict egress. Credential protection is a separate obligation and must not be presented as satisfied by the isolation level. See [`docs/security-threat-model.md`](../../security-threat-model.md) T3.
* **Why**: Developers need instant local startup, and coordinating agents on one machine must not pay the cost of a network hop or an external broker round-trip merely to dispatch an in-process event. This is a structural requirement, not a numeric one — the law is that dispatch stays in-process, and it is falsifiable by inspection: any single-machine code path that hands an event to an out-of-process broker to reach another local agent violates this principle, regardless of how fast that broker is.
* **Numeric targets live elsewhere**: This principle does not fix a latency number. Concrete, revisable performance budgets for dispatch overhead and for agent turn latency are defined in [`docs/nfr-performance-budgets.md`](../../nfr-performance-budgets.md), which principles reference by name rather than encode. A tuning constant is not law; only the zero-broker *requirement* above is.
